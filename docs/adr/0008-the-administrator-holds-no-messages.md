# The administrator holds no messages

A Message Crate has exactly one administrator, `admin`, at a fixed well-known
account id, made when the database is made, and it has no store of its own: no
conversations, no contacts, no import, no export, no trash, and no API tokens.
The administrator sets the server settings, creates, disables and deletes
accounts, resets their passwords, and deletes their message data. It monitors
the installation: how much each account holds and what each account has been
doing. It never reads a message. A Message Crate whose administrator has no
password is in setup and offers only setting it; after that it is ready.

## Why

Before this decision an administrator was an ordinary account carrying
`accounts.is_admin = 1`. Any number of accounts could carry it, the first
non-demo account to register was promoted to it automatically, and an
administrator could import, export, browse and delete message data like anyone
else, because the flag granted extra powers without removing any. The only
protection on the role was `is_last_admin`, which refused the change that would
leave the installation with no usable administrator — so an administrator could
still be deleted whenever a second one existed.

Three properties of that model were wrong for a self-hosted product.

The person who installs the software is not automatically the person whose
messages it holds, and silently promoting whoever registered first
conflated the two. Making the administrator an account of its own, `admin`,
separate from every account that holds messages, states which one is
happening.

An administrator who can also import, export and read can reach another
person's messages the moment a second account is created for them. Removing
the administrator's store rather than restricting access to it is the only
version of the restriction that cannot be undone by flipping a flag.

An arbitrary number of administrators is an invariant to police forever. One
administrator at a fixed id is an invariant that holds by construction:
"exactly one" and "cannot be deleted" become a comparison against a constant,
the same mechanism `is_demo_account` already uses for `DEMO_ACCOUNT_ID`.

## How the administrator is modeled

The administrator is a row in `accounts`, so login, session tokens, password
hashing and password change work unchanged. The row is written when the
database is made, with the username `admin` and no password. What separates
the administrator is the credential it resolves to. `AuthCapability` has a
third variant, `Admin`, carrying no `Permissions` at all, alongside
`Session { permissions }` and `ApiToken(permissions)`.

Every guard generated by `auth_guard!` that asks for a permission —
`ImportAccess`, `ExportAccess`, `FullAccess`, `FullDeleteAccess` — rejects
`Admin`, because there are no permissions on it to satisfy them. The `Admin`
guard accepts only `Admin`. A route the administrator must not reach therefore
cannot be reached by accident: refusal is the default, and admitting the
administrator takes a deliberate guard. `accounts.is_admin` is deleted, along
with `is_last_admin` and its call sites, because being the administrator is
the account id and nothing grants it.

Two routes need a guard that admits either the administrator or an ordinary
session, `LoggedIn`: `PUT /v1/accounts/{id}/password` and the account profile
routes. Those are the only places where the administrator acts on its own
account rather than someone else's.

`AuthCapability::ApiToken` is unchanged, which means the administrator can
never mint a token and no token can ever act as the administrator. A leaked
API token stays bounded by the message-data permissions of the one account
that issued it; it cannot reach the account list. The administrator restrains
an account by clearing its `can_import` or `can_export`, and every token that
account already issued narrows with it, because token permissions are
intersected with the issuing account's on every request.

## What the administrator may see

The administrator sees metadata and never content. (Revised 2026-09-19. Until
then the rule was narrower: a message count and a storage total per account,
and nothing else.)

The administrator administers the installation, and administering it means
knowing how much data it holds and what its accounts have been doing. A count
and a byte total per account answer neither question well: they do not say
which import doubled an account's size, whether an account has exported
everything it holds, or which files fill the disk. So the administrator may
read anything that describes an account's data without being that data:

- counts and totals: messages, conversations, contacts, attachments, and the
  bytes each takes, per account and for the whole database;
- activity: each import and export an account has run, with its source,
  format, time, outcome and the counts it reported, and when the account last
  logged in;
- attachments as files: name, type, size and date.

The administrator may not read what a person wrote or whom they wrote to:

- a message's text, subject or transcription, and any search over them;
- an attachment's bytes, a thumbnail or a preview of it;
- a contact's name, handles or photo, and which contacts a conversation is
  between.

An attachment's file name sits on the permitted side on purpose. A name can
say something about its file, and the administrator needs it anyway: "the
disk is full" is answered by naming the files that fill it, and a size with
no name cannot be acted on. Contacts sit on the other side. How many contacts
an account has is a measure of the database; who they are is the account
holder's address book.

Why the server could not make an attachment's Thumbnail or Preview sits on
the permitted side too. (Revised 2026-10-12, #2636.) The administrator reads,
for each Import Run, the attachments it wrote whose versions were not made,
each by its name, type and size, with the kind of failure and the reason the
server recorded. The reason is what ffmpeg said about the file, with the
paths it named made relative to the account's directories, or a phrase of
the server's. It describes the file as a file, as its type and size do, and
never holds what the file shows or which conversation it is in. The
administrator needs it to tell a damaged backup from a slow computer, and to
decide whether to try again. The attachment's bytes, its Thumbnail and its
Preview stay on the other side.

An Import Run's log is the one place the administrator reads a conversation's
identities. (Revised 2026-10-09. Until then whether the administrator may read
them was open in
[#1990](https://github.com/messagecrate/message-crate/issues/1990).)
A run log may name the conversation files and attachments the run read. A
conversation file is named for the people in it, so its name can carry a
phone number, an email address or a group's title. The administrator reads
those names in the log. Why: the file name is part of what explains a
failure. The log is a plain file in the Logs Directory of the computer the
account imported from. The operating-system user who ran the import can open
it with or without Message Crate, and the administrator reads it in the
desktop app running as that user. While the run lasts, the Staging Directory
holds the same names. Keeping them off the administrator's screen would
protect nothing.

Nothing in the administrator's routes reads `messages.body`,
`attachments.transcription`, or any other content column. A new
administrator route is judged by the two lists above, and a column that fits
neither is content until this ADR says otherwise.

The rule holds even where it costs the administrator something. The
administrator can delete an account's message data without being able to
look at it first, and so deletes on the strength of the counts, the import
history and the account holder's word, not on inspection.

All of this is built. An account's Storage tab shows the administrator what it
shows the account holder: the message, attachment, conversation and contact
counts and the storage total, each import and export the account has run, the
attachments of each import that have no Thumbnail or Preview and why, and its
largest attachments by name and size. The administrator reads them at
`/v1/accounts/{id}/storage`, `/imports` and `/exports`; `/v1/imports` and
`/v1/exports` stay the pipelines' own and still refuse the administrator. Two
things on that screen say who the account talks to, and the administrator gets
neither: an import's detail gives the administrator how many contacts it
created and changed and not who they are, and a large attachment comes to the
administrator as a name, a type and a size, without the conversation it is
in. A run in the history comes to the administrator as a type of its own,
`AdminImportRun` or `AdminExportRun`, holding the source, mode, tool, times,
outcome and counts: an import's summary lists the addresses in the backup, its
issues name conversations, and an export's query is a search over the
account's messages, so none of them reach the administrator through the
server. The run log on the importing computer names the conversation files
(above). The installation-wide totals are `GET /v1/server/storage`, the
administrator's alone, and Admin Home's Dashboard shows them. The per-account
and installation-wide numbers come from the same queries
(`crates/server/server/src/db/storage.rs`), with and without an account
filter, so the Dashboard cannot disagree with the sum of the Storage tabs.

## The two states of a Message Crate

`GET /v1/server` is unauthenticated and reports one value: `setup` or
`ready`. The logged-out screen follows from it: in setup the login card sets
the administrator's password, and when ready it logs in.

The server reports the state rather than the fact behind it (whether `admin`
has a password) so that the rule is stated once. A browser and a desktop app
that each derived the screen from raw fields would be two copies of one rule,
free to drift apart.

Whoever reaches a Message Crate in setup first may set the administrator's
password. It is self-hosted: its operator installs the software, sets the
password, and publishes the port, in that order and at times of their
choosing. A race that requires exposing an unconfigured server to a hostile
network and then walking away is a configuration the operator chose. A
Message Crate in setup is also empty, so a lost race destroys nothing and
announces itself immediately — the operator finds they cannot set up their
own installation. `set-admin-password` on the server takes it back.

## Considered and rejected: a separate administrator table

Keeping the administrator outside `accounts` entirely would make it impossible
for the twelve account-scoped data tables to reference the administrator at
all, rather than merely leaving those rows unwritten. It would also require a
parallel session-token table, a parallel login handler, and an `AuthIdentity`
whose `account_id` is no longer an account id, which every extractor would
have to account for. The `Admin` capability variant already makes "the
administrator cannot touch message data" a fact the type system checks.
Structural impossibility was not worth a second login path.

## Considered and rejected: three zeroed permission flags

Provisioning the administrator with `can_import`, `can_export` and
`can_delete` all `0` is the cheapest version of the same restriction. It was
rejected because "the administrator holds no messages" would then be a fact
about three boolean values that anything with database access can change,
rather than a property of the design.

The administrator's row does hold 0 for all three columns, so someone reading
the database sees what the server grants. The zeros are not the mechanism:
the server decides the administrator's permissions from its id and ignores
those columns for it, so setting one to 1 grants nothing. (Revised
2026-10-11. Until then the row held the columns' defaults of 1
([#2577](https://github.com/messagecrate/message-crate/issues/2577)).)

## Considered and rejected: a setup token

Printing a token to the server log on first start and requiring it to set the
administrator's password defends against a silent compromise. Setup is not
silent: the operator discovers it immediately, on an empty database, and
wipes the volume or runs `set-admin-password`. The token would add a
`docker logs` step to a quickstart that currently has none, in exchange for
closing a window whose width the operator sets.

## Considered and rejected: invite links

Letting the administrator issue a code the new person redeems, choosing their
own password, means the administrator never learns anyone's password. Invites
need a table, an unauthenticated redeem route, and a code handed over out of
band anyway. They are deferred, not rejected, and become the better answer
once the server can send mail. Until then the administrator chooses the
password, hands it over, and the person keeps it until they change it under
Settings; the server does not force that change. (An earlier version marked
the account with `must_change_password` and made the holder replace the
administrator's password at first login; that mark was removed as more
ceremony than a self-hosted product needs.)

## Consequences

- Only the administrator creates accounts; there is no self-service
  registration (its former design is recorded in #3248). `POST /v1/accounts`
  takes the administrator's Session and nothing else.
- The administrator must have a password, of one character or more, and
  cannot clear it. A user account has no minimum and may have no password,
  but an account with no password cannot log in until the administrator sets
  one under its Settings. Only the Demo Account enters without a password.
  (An earlier version had the demo seed write the administrator with the
  password `admin`;
  `docs/adr/0016-the-demo-account-is-fixed-not-configured.md` removed that,
  and the database now makes the administrator itself.)
- The administrator can delete the demo account and its data. The demo
  account still cannot delete itself.
- The administrator leads the account list it manages, ahead of the rest by
  username. The administrator is an account too, and its row is how the
  administrator reaches its own Settings, the same way it reaches anyone
  else's. The row has no status and no permissions to set: the administrator
  cannot be disabled, and holds no messages to import, export or delete.
  (Until 2026-09-19 the administrator was left out of the list, on the
  grounds that it is not one of the users.)
- An account's name in that list opens the account's Settings, laid out as
  its holder sees them. The administrator sets the account's password there,
  its status and its import, export and delete permissions, and deletes its
  messages or the account. The list itself sets nothing. The account holder
  sees the same Status and Permissions sections with nothing to change, so
  what an account may do is stated to the person it binds. The administrator
  sets the account's name, time zone and handles as the holder does, so an
  account can be handed over ready to import into; the holder's own profile
  setup at first login is still owed. (Until 2026-09-19 all three were the
  account's own to set, and the administrator only read them.) The
  administrator reads there when the account last logged in and which app it
  connects with.
  Storage shows the administrator what it shows the holder: how much the
  account stores, its import and export history, and its largest attachments'
  names and sizes. The administrator sees the account's API tokens on its
  Account tab, each with its label, permissions and use, and revokes one, so
  a leaked token can be ended; it never sees any part of a token's secret, and
  makes and renames none, because a token is the holder's credential. A
  token's label and permissions are not message content. (Until 2026-10-02
  the administrator saw no API tokens at all.) The administrator sees no
  address book, which is content. The tabs that belong to a device rather
  than an account (System, Convert, Appearance) are not shown for a managed
  account.
- The administrator's own Settings are Account, Profile and Appearance.
  Storage, System and Convert work on messages, and Profile has no handles
  and no address book, for the same reason: there are no messages for a
  handle to claim. Changing the administrator's password takes the current
  one, checked by the server, because that account reaches every other and an
  open session must not be enough to take it over. A user account changes its
  own on its session alone.
- A forgotten administrator password cannot be reset from inside the product,
  because no account stands above the administrator.
  `message-crate-server set-admin-password` sets it from a shell on the
  server, which is the credential the administrator already holds as the
  operator. It does both jobs: on a Message Crate in setup it sets the first
  password, and on a ready one it replaces the password and ends the
  administrator's Sessions, so a lost password is recovered and a leaked one
  stops working in one step.
- The administrator surface is named for what it returns: `/v1/accounts`, the
  `Accounts` OpenAPI tag, `accounts_api.rs`, and the `Admin` guard. The
  interface says accounts because it returns account records; the screen says
  User Accounts because it lists the people who use the installation.
- The administrator logs in to Admin Home, a screen of its own, not to the
  message-browsing shell. The account-management screen leaves Settings, and
  an ordinary account loses it entirely, because an ordinary account can no
  longer be an administrator.

## Amended (2026-10-24)

The owner became the administrator, `admin`, a fixed username on the fixed id,
made with the database instead of by a claim; setup replaced claiming; and
public registration was removed. The design of registration as it was is
recorded in #3248.
